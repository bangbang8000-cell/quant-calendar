## 2. 战略背景

### 2.1 从"好用"到"可信·自动·开放"

v3.0 ~ v3.9 完成了核心业务闭环、前端组件化、移动端 PWA 与安全基线。v3.10 ~ v4.0 的战略目标是 **从"个人可用产品"升级为"可信赖的决策系统"**：

- **v3.10 可信**：核心引擎（美林时钟）此前零测试保护，是唯一没有回归护栏的核心资产；依赖未锁定导致不可复现；数据源失败仅静默 fallback。
- **v3.11 自动**：数据仍依赖手工 CSV，是产品化最大短板——本阶段打通 tushare 定时拉取 → 自动生成 qresult → 自动入库的全自动数据闭环。
- **v3.12 可运维**：备份无恢复入口、异常无告警、部署靠手工——补上最后一块运维拼图，实现可观察、可告警、可回滚。
- **v3.13 智能**：AI 多模型评估串行低效，通知渠道单一——并行化释放性能，通知矩阵扩展触达。
- **v4.0 开放**：从封闭应用到开放平台——API 契约化、出站 Webhook、插件机制。

### 2.2 演进策略

沿用 **"每版本只做一件事，小步提交，可回滚，验证先行"** 原则。版本主题与定位：

| 版本 | 主题 | 定位 |
|------|------|------|
| v3.10 | 可靠性加固 | 修风险（核心引擎测试 + 依赖锁定 + 数据源监控） |
| v3.11 | 数据自动化 | 消灭手工 CSV，实现 T+1 全自动数据闭环 |
| v3.12 | 可观测与部署 | 备份可恢复 + 异常可告警 + 部署可回滚 |
| v3.13 | AI 深化与通知矩阵 | 并行评估提速 + 多通道触达 + RAG 问股 |
| v4.0 | 开放平台 | API 契约 + 出站 Webhook + 插件机制 |

## 3. v3.10 — 可靠性加固

### 3.1 需求概述

v3.10 不做新功能，专注 **消除 P0 风险**：核心引擎测试从 0 到 ≥70%，构建可复现，数据源可观测。

### 3.2 功能需求

#### FR-3.10.1 — 美林时钟引擎测试补齐
**现状**: `merrill_clock.py`（~900 行，经济周期判定核心引擎）无专门测试文件；`determine_stage()` 全分支未覆盖；v3.8.2 接线的 `time_driven` 时间驱动切换逻辑无回归保护。
**需求**: 新增 `tests/test_merrill_clock.py`，覆盖：四象限判定、信心度计算、下一阶段预测、早期预警、边界驱动切换、时间驱动切换、快照持久化；测试文件须重定向到临时数据文件，不污染 `data/` 运行时数据。
**验收**: 核心引擎语句覆盖率 ≥ 70%；时间驱动/边界切换分支有显式断言。
**文件**: `tests/test_merrill_clock.py`, `tests/conftest.py`

#### FR-3.10.2 — 依赖锁定
**现状**: `requirements.txt` 全部为 `>=` 未锁定，Docker 每次构建拉取最新 minor，结果不可复现、存在隐式回归源。
**需求**: 引入 `pip-tools`（或 `uv`）生成锁定文件；Docker 与 dev 双端按锁文件安装。
**验收**: 同一锁文件两次构建依赖哈希一致；CI 校验锁文件未漂移。
**文件**: `requirements.in`, `requirements.lock`, `Dockerfile`, `.github/workflows/ci.yml`

#### FR-3.10.3 — 数据源健康监控
**现状**: AKShare/Tushare 拉取失败仅 log 后 fallback（实测 `akshare` 上游属性改名即报错降级），无结构化指标，运维不可见。
**需求**: 数据源调用封装为可观测层，记录 success/latency/error 指标，输出到系统监控 API；连续失败标记 degraded 状态。
**验收**: `/api/system/metrics` 出现各数据源成功率/延迟；模拟失败后 degraded 标记可见。
**文件**: `backend/data_sources.py`, `backend/system.py`, `backend/merrill_clock.py`

#### FR-3.10.4 — CI 覆盖率门禁
**现状**: CI 仅跑 ruff + pytest，无覆盖率门禁，核心模块回归无强制保护。
**需求**: `ci.yml` 增加 `pytest-cov` 并设置核心模块覆盖率阈值，低于阈值 CI 失败。
**验收**: CI 输出覆盖率报告；人为删用例后 CI 变红。
**文件**: `.github/workflows/ci.yml`, `pyproject.toml`

#### FR-3.10.5 — 版本号前后端统一
**现状**: 后端已有 `APP_VERSION` 单一来源（v3.8.2 接线），但前端 `index.html` 资源缓存号（`?v=3.8.2`）仍手工硬编码，发布时易漏改。
**需求**: 前端资源版本号改为由后端注入（随 index.html 模板渲染），与 `APP_VERSION` 联动。
**验收**: 修改 `APP_VERSION` 后前端资源 URL 自动带新版本号。
**文件**: `backend/main_new.py`, `frontend/index.html`

## 4. v3.11 — 数据自动化

### 4.1 需求概述

打通 **tushare 定时拉取 → 自动生成 qresult → 自动导入** 的全自动数据闭环，消灭手工 CSV；数据新鲜度可视化。

### 4.2 功能需求

#### FR-3.11.1 — Tushare 定时拉取管线
**现状**: `qresult` 持仓 CSV 由外部量化策略程序手动生成、手动放置；数据新鲜度依赖人工，是产品化最大短板。
**需求**: 新增定时拉取任务：按配置的股票池/频率从 tushare 拉取日线 + 财务数据，自动生成/更新 `qresult` CSV，并触发 `data_pipeline` 自动入库；支持数据源配置界面（股票池、拉取频率、启用开关）。
**验收**: 手动触发后 `qresult` 目录出现新数据且自动入库；定时任务按配置执行；日志记录每次导入批次。
**文件**: `backend/data_sources.py`, `backend/data_pipeline.py`, `backend/scheduler.py`, `backend/data_refresh.py`, `frontend/js/components/system-page.js`

#### FR-3.11.2 — 数据新鲜度看板
**现状**: 无数据新鲜度可视化，用户无法判断数据是否过期。
**需求**: Dashboard 增加数据源状态卡：每数据源 `last_success` / `last_fetch` / 数据年龄 / 成功率；超过配置阈值标黄警示。
**验收**: 首页可见各数据源新鲜度；模拟数据过期后状态卡标黄。
**文件**: `backend/api/v1/dashboard.py`, `backend/system.py`, `frontend/js/components/dashboard-page.js`

#### FR-3.11.3 — 拉取失败补偿
**现状**: 数据拉取失败仅单次 fallback，无重试与补偿。
**需求**: 拉取失败自动重试（指数退避，最多 3 次）；连续失败写入告警队列，供 v3.12 通知通道消费。
**验收**: 模拟连续失败 3 次后停止重试；告警队列出现记录。
**文件**: `backend/data_sources.py`, `backend/scheduler.py`

## 5. v3.12 — 可观测与部署

### 5.1 需求概述

补上运维最后拼图：**备份可恢复、异常可告警、部署可回滚**，让部署不再是黑盒。

### 5.2 功能需求

#### FR-3.12.1 — 备份恢复闭环
**现状**: `backup.py` 已实现自动备份，但无恢复入口与演练，一旦数据损坏无法自助恢复。
**需求**: 系统设置页增加备份列表 + 一键恢复按钮；恢复前 dry-run 校验（备份完整性 + schema 兼容），校验失败拒绝恢复。
**验收**: 备份列表可见；执行恢复后数据一致；dry-run 演练通过。
**文件**: `backend/api/v1/system.py`, `backend/backup.py`, `frontend/js/components/system-page.js`

#### FR-3.12.2 — 异常告警通知
**现状**: 500 错误率、数据源连续失败等异常无主动告警，问题依赖用户发现。
**需求**: 阈值触发告警：500 错误率 > 1% 或数据源连续失败（消费 FR-3.11.3 告警队列）→ 飞书推送；告警收敛（同主题合并，防刷屏）。
**验收**: 故意制造错误后飞书收到告警；同主题重复告警被合并。
**文件**: `backend/scheduler.py`, `backend/feishu_push.py`, `backend/system.py`

#### FR-3.12.3 — 一键部署/回滚
**现状**: dev→ops 同步靠手工 `git checkout` + nohup 重启，无校验、无回滚，失败即服务中断。
**需求**: `scripts/deploy.sh`：拉取 → 语法校验 → health-gated 重启 → 健康检查失败自动回滚到上一提交；`scripts/rollback.sh` 手动回滚。
**验收**: 模拟失败部署自动回滚，服务不中断；rollback 脚本可用。
**文件**: `scripts/deploy.sh`, `scripts/rollback.sh`

#### FR-3.12.4 — 系统监控面板 UI 完善
**现状**: 系统监控 API（CPU/内存/请求延迟/错误率）已存在，但前端面板展示不完整。
**需求**: 完善系统设置页监控面板：CPU/内存/磁盘、API 延迟曲线、错误率、各数据源状态；自动刷新。
**验收**: 面板显示全部指标并自动刷新；与 `/api/system/metrics` 数据一致。
**文件**: `frontend/js/components/system-page.js`, `backend/api/v1/system.py`

## 6. v3.13 — AI 深化与通知矩阵

### 6.1 需求概述

多模型并行评估释放性能，通知渠道从单一飞书扩展为矩阵，智能问股引入 RAG 检索增强。

### 6.2 功能需求

#### FR-3.13.1 — 多模型并行评估
**现状**: 8+ AI 模型**串行**逐个评估，单股耗时 ~2s+，等待感明显。
**需求**: `asyncio.gather` 并行调用 + 超时保护 + 部分失败降级；结果聚合逻辑与串行版一致。
**验收**: 单股评估耗时显著下降（目标 ÷3）；部分模型失败不影响整体结果返回。
**文件**: `backend/ai_evaluator.py`

#### FR-3.13.2 — 通知渠道抽象
**现状**: 通知仅飞书（`feishu_push.py`），日报/周报/告警无法触达非飞书用户。
**需求**: 通知适配器接口（飞书/企业微信/钉钉/邮件/Webhook），配置驱动，模板化；日报/周报/告警均可达多通道。
**验收**: 配置企微/钉钉/邮件后，日报与告警可送达对应渠道。
**文件**: `backend/notify/`（新目录）, `backend/scheduler.py`, `backend/api/v1/user_config.py`

#### FR-3.13.3 — RAG 问股（第一阶段）
**现状**: 智能问股基于单股上下文，无法引用历史报告与策略知识。
**需求**: 构建策略知识库 + 历史报告检索（轻量向量/关键词混合），问股时检索增强回答。
**验收**: 问股回答能引用相关历史报告/策略知识片段。
**文件**: `backend/chat.py`, `backend/ai.py`, `backend/search.py`

## 7. v4.0 — 开放平台

### 7.1 需求概述

从封闭应用到开放平台：API 契约化、出站 Webhook 订阅、最小插件机制，为第三方集成铺路。

### 7.2 功能需求

#### FR-4.0.1 — API 契约版本化与文档站点
**现状**: FastAPI 自动生成 OpenAPI，但无版本化契约（升级即破坏）、无独立文档站点。
**需求**: 新增 `/api/v2` 前缀承载新契约，v1 保持向后兼容；独立文档站点（定制 redoc/mkdocs）含示例代码。
**验收**: `/api/v2` 可用且 v1 接口全部兼容；文档站点可浏览。
**文件**: `backend/router.py`, `backend/main_new.py`, `docs/`

#### FR-4.0.2 — 出站 Webhook 订阅
**现状**: 通知只进不出，无法对外推送行情/信号。
**需求**: 用户配置 Webhook URL 订阅（策略信号/日周报/美林阶段切换），回调带签名校验与重试。
**验收**: 配置 Webhook 后收到带签名的回调；非法签名被拒绝。
**文件**: `backend/notify/`, `backend/scheduler.py`, `backend/api/v1/user_config.py`

#### FR-4.0.3 — 最小插件机制
**现状**: 策略与 AI 模型均硬编码注册，无法扩展。
**需求**: 定义插件协议（策略插件 / AI 模型插件），白名单目录动态加载，插件出现在对应列表。
**验收**: 样例插件可加载并出现在策略/AI 模型列表。
**文件**: `backend/plugins/`（新目录）, `backend/router.py`

## 9. 验收标准

每个版本验收需满足：
1. **所有 FR 通过**（功能需求逐项验证）
2. **SPA 完整性检查通过**（template/div/dual 脚本）
3. **pytest 全量通过**（无 regression）
4. **浏览器冒烟**（SM-1 ~ SM-15 + 各版本专项）
5. **GitHub Actions CI 通过**（v3.10 起含覆盖率门禁）
6. **每版本打 tag 触发 docker-publish**
