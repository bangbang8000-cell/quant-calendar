## 10. 部署验收与回滚

### 10.1 每次发布的标准流程

1. `python scripts/bump_version.py <ver>` → 校验 `APP_VERSION`（`backend/main_new.py`）、README 首行、`docs/HANDOVER.md` 状态、tag；
2. L1–L4 门禁全绿；
3. dev（8001）验收 → ops（8000）部署；
4. 部署后 90s 内 `/api/health` = 200 且 `version` 为新版本；
5. 冒烟：关键旅程 1–3；
6. `git tag v<ver>` → 推送 `origin`（GitHub）+ `synology`（群辉 `ds1522plus`）；
7. ops 镜像仓库同步 checkout 对应 tag；
8. 更新 `MILESTONES.md` / `FEATURE-MATRIX.md` / `TEST-CASES.md`。

### 10.2 回滚

| 项 | 策略 |
|---|---|
| 代码 | `git checkout v<上一版>` + 重启；实测 39–56s（`scripts/rollback_drill.py`） |
| 数据 | 本轮**不改表结构**，新增字段均为可选列/新文件；`freshness.json`、`scheduler_history.json` 写入前保留 `.bak` |
| 配置 | 导航组配置迁移前备份 `data/groups.json.bak`；迁移脚本支持 `--rollback` |
| 触发条件 | 健康检查失败 / 关键旅程失败 / 错误率 >5% / 数据写入异常 |

## 11. 提交拆分与版本治理

每个版本 3–8 个语义化提交（`<type>(<scope>): <desc>`），示例（6.4.1）：

```
feat(scheduler): 自动刷新开关与作业注册
feat(scheduler): 失败退避重试与连续失败告警
fix(freshness): 刷新成功后原子更新并触发视图重载
feat(freshness): 陈旧数据决策护栏（角标/导出留痕/AI 标注）
feat(ops): 服务自启与崩溃自愈脚本
feat(api): health 扩展版本/运行时长/自检摘要
test(quality): 6.4.1 用例与门禁
chore(release): bump v6.4.1
```

纪律：一次提交只做一件事；不混"格式化"与"逻辑变更"；`chore(release)` 必须最后单独提交。
