## 3. 逐项根因分析

### 3.1 P0-1 「我的自选 共 13 只」无法正常加载和显示

#### 3.1.1 现象（实测两组对照）

在 ops（:8000）用 admin 登录后进入「智能评估 → 我的自选」：

| 观测项 | 组 A：SPA 登录后**不刷新** | 组 B：登录后 **F5 刷新** |
|---|---|---|
| 标题计数 | 共 13 只 | 共 13 只 |
| 列表行数 `.watchlist-item` | **13** | **13** |
| 报价行 `.watchlist-quote` | **0** | **13** |
| 实时报价条 | `实时报价 / 连接中...` | `实时报价 / 实时` |
| 实际建立的 WebSocket | **`[]`（一条都没建）** | `ws://.../api/market/ws/quotes` |
| 首行报价内容 | 无 | `14.05 / -1.54% / 量比 1.18 / 涨速 --%` |

即：**列表 13 只是对的，价格/涨跌幅/量比整层空转**。用户看到「共 13 只」但内容区没有任何行情，观感就是「无法正常加载和显示」。

#### 3.1.2 根因（已定位到行）

`frontend/js/watchlist/realtime.js` 全文只有**一处**触发连接，且在模块求值（页面加载）时立即判定：

```js
// realtime.js:182-184
if (_realtimeToken()) {
  setTimeout(connectRealtimeQuotes, 500);
}
```

- 页面首次加载时**尚未登录**，`localStorage.quant_token` 不存在 → 该分支不进入；
- 用户随后走 SPA 表单登录，`frontend/js/app-logic/auth.js` 的 `handleLogin()` / `handleGuestLogin()` 只写 `localStorage.quant_token`，**从未调用 `connectRealtimeQuotes()`**；
- 唯一的重连路径是 `ws.onclose` 里的退避重试（`realtime.js:167-176`），但连接从未发起 → 没有 `onclose` → 永远不会重试。

于是 `realtimeWsState` 恒为初始值 `'idle'`，而模板只区分三种状态：

```html
<!-- frontend/js/components/ai/view-part2.js:139-146 -->
<span v-if="realtimeDegraded || realtimeWsState === 'offline'" ...>降级文案</span>
<span v-else-if="realtimeWsState === 'open'" ...>实时</span>
<span v-else class="rt-connecting">连接中...</span>   <!-- ← idle 落到这里 -->
```

`idle`（从未发起）被渲染成「连接中...」，**把「没开始」伪装成「正在连」**，用户无法判断是网络慢还是功能坏了。

#### 3.1.3 为什么不是后端问题（已排除）

在页面上下文直接 `new WebSocket('ws://.../api/market/ws/quotes?token=...')`，服务端表现完全正常：

```
events: ["open",
  "msg:{type:quotes, data:[{code:600869.SH, price:14.05, change_pct:-1.54, volume_ratio:1.18}, ...], full:true}",
  "msg:{type:quotes, data:[], delta:true}"]
```

订阅、全量快照、增量帧、心跳全部正常。**缺陷纯在前端连接时机**。

#### 3.1.4 修复方向

| 项 | 方案 |
|---|---|
| R1 | `handleLogin()` / `handleGuestLogin()` 成功后调用 `qcState.connectRealtimeQuotes()`（该函数**已注入 qcState**：`app-logic.js:227/421`，无需新增导出） |
| R2 | 增加「认证态 watch」兜底：`watch(currentUser, ...)` 或 token 变化即连接/断开，避免后续新增登录入口再次漏接 |
| R3 | 增加状态看门狗：`connecting` 超时（建议 8s）→ 置 `offline` + 降级文案，不再无限「连接中」 |
| R4 | 文案区分三态：「未连接（未登录）」「连接中」「已断开」，`idle` 不再复用「连接中」 |
| R5 | 登出时调用 `disconnectRealtimeQuotes()` 并清空 `realtimeQuotes`（现有函数已具备） |
| R6 | 补守护用例：`测试：登录成功后必须发起 WS / 登出后必须断开`（当前**无用例**覆盖，故回归未被发现） |

### 3.2 P0-2 美林时钟「历史和现状」需重新评估、计算和更新

#### 3.2.1 现象

线上 `/api/market/merrill-clock` 返回：

```json
{
  "name": "衰退期", "stage": "recession",
  "indicators": { "pmi": 50.8, "industrial_added": 5.1, "m2_growth": 9.8,
                  "gdp_growth": 0.0, "cpi": 0.0, "ppi": 0.0, "social_financing": 0.0,
                  "_data_source": "AKShare实时数据" },
  "dimension_scores": {
    "growth":    {"score": -1.11, "level": "低位", "details": {"gdp_growth": {"value": 0.0, "z_score": -3.33}}},
    "inflation": {"score": -1.10, "level": "偏低", "details": {"cpi": {"value": 0.0, "z_score": -1.5}}},
    "liquidity": {"score": -1.28, "level": "收紧", "details": {"social_financing": {"value": 0.0, "z_score": -5.0}}},
  },
  "confidence": {"level": "高", "weighted_score": -0.7}
}
```

矛盾点直白可见：**PMI 50.8（扩张）、M2 同比 9.8%（宽货币），系统却给出「流动性 收紧」「增长 低位」，并以「高置信度」判定为「衰退期」**。

#### 3.2.2 根因一：取数列名/字段与 AKShare 现状不符，且缺省值 0 静默覆盖

直接调用后端函数（不是 UI 问题）：

```python
>>> merrill_clock._fetch_real_macro_data()
{'cpi': 0.0, 'ppi': 0.0, 'gdp_growth': 0.0, 'social_financing': 0.0,
 '_data_source': 'AKShare实时数据', ...}
```

再直接打印 AKShare 真实列名比对：

| 指标 | 代码假设（`_indicators.py`） | AKShare 实际列名 | 结果 |
|---|---|---|---|
| CPI | `latest.get('全国', 0)`（L76） | `['商品','日期','今值','预测值','前值']` | **恒 0**（列不存在） |
| PPI | `latest.get('全国', 0)`（L85） | 同上 | **恒 0** |
| GDP | `latest.get('国内生产总值同比增长', 0)`（L105） | `['季度','国内生产总值-绝对值','国内生产总值-同比增长', …]`（**带连字符**） | **恒 0** |
| 社融 | `latest.get('社会融资规模存量同比增长', 0)`（L143） | `['月份','社会融资规模增量', …]`（只有**增量**，无**存量同比**） | **恒 0** |
| 工业增加值 | `ak.macro_china_industrial_production`（L111） | **该属性不存在**（`AttributeError`） | 静默缺失 |

叠加两个结构性缺陷：

- **缺 `> 0` 守卫**：PMI 分支有 `if pmi_val > 0` 保护（L63），而 CPI/PPI/GDP/社融**无条件赋值**，于是「取不到」被写成「等于 0」；
- **零值反向覆盖**：`_indicators.py:223` 的 `indicators.update(real_data)` 用 0.0 覆盖了 L188-200 里本已合理的默认值（GDP 5.3 / CPI 0.8 / PPI 0.3 / 社融 10.2）。**默认值本来是对的，是"真实数据"把好数据覆盖坏了。**

补充证据（数据方向性错误）：`macro_china_gdp` 的 DataFrame 是**降序**（`tail()` 返回的是 `2006年第1季度`）。即使把列名改对，`iloc[-1]` 仍会取到 **2006 年**的最旧记录——说明该处**还缺一次排序**。

#### 3.2.3 根因二：零值把 z-score 打穿，维度评分与阶段判定连锁失真

`_indicators.py:276-313` 用的是固定基准的标准化：

```
gdp_z  = (0.0  - 5.0)  / 1.5  = -3.33
cpi_z  = (0.0  - 1.5)  / 1.0  = -1.50
sf_z   = (0.0  - 10.0) / 2.0  = -5.00
```

零值不是「中性」，而是**极端悲观**。于是 `growth=-1.11`、`liquidity=-1.28`，加权后 `weighted_score=-0.7`，落在「衰退期」象限，还给出「置信度高」。

#### 3.2.4 根因三：阶段边界无防抖，0/1 天阶段污染历史

ops 的 `data/merrill_history.json` 已有 **18 条**转移，其中：

| 转移日期 | 路径 | 该阶段持续 | 触发 |
|---|---|---|---|
| 2026-10-22 | 衰退 → **过热** | 83 天 | `boundary`（自动） |
| 2026-10-23 | 过热 → **衰退** | **0 天** | `boundary` |
| 2026-10-29 | 衰退 → **过热** | 6 天 | `boundary` |
| 2026-10-30 | 过热 → **衰退** | **1 天** | `boundary` |

**「持续 0 天」和「持续 1 天」的经济周期阶段在业务上不成立**。dev 侧同样有 `2026-08-11 复苏→衰退`（`trigger: boundary`）。这些抖动会直接画进「本轮演进」时间轴与甘特条，让历史看起来像噪声。

#### 3.2.5 根因四：历史与现状自相矛盾

- 静态史表 `HISTORICAL_TRANSITIONS` 最后一条是 **2024-09-24 衰退→复苏**；
- 运行时 `current_stage` = **recession（衰退期）**；
- UI「本轮演进」同时画出：`衰退期 23.00 月 → 复苏期 25.00 月 → 剩余(预测) 复苏期`，而当前阶段徽标却是「衰退期 · 已过 0 天 · 进度 0.00%」。

三套口径（静态史表 / 运行时状态 / 时间轴）互不一致，这正是用户所说的「历史和现状需要重新评估」。

#### 3.2.6 根因五：数据溯源标签失真

`_data_source: "AKShare实时数据"` 会让用户以为 17 项指标全是实时真实值，实际其中 **4 项是解析失败后的 0**。数据可信度未在接口与 UI 中暴露。

#### 3.2.7 修复方向

| 层 | 方案 |
|---|---|
| L1 取数 | 按 AKShare **当前列名**取数；每指标支持**多列名兜底链**（如 `今值 → 前值`，`国内生产总值-同比增长`）；统一 `_pick_latest(df, col)`：先按日期/季度**升序排序**再取最后一行；`NaN` 跳过；**取不到就「不写入」**，绝不写 0 |
| L2 缺失语义 | 引入 `missing: [...]` 与 `quality: "full｜partial｜fallback"`；未取到的指标保留默认值但**标记为估计值**，不伪装成实时 |
| L3 评分 | 维度评分按**可用指标加权**（或整维缺失则剔除该维并按剩余维重归一）；零值绝不参与 |
| L4 阶段防抖 | 边界切换加**滞回 + 连续确认**（建议：新象限需连续 ≥3 次评估 / ≥5 个交易日确认）+ **最小阶段时长**（建议 ≥20 交易日）+ 切换冷却期；低置信度不得改写历史状态 |
| L5 历史订正 | 清理 2026 年 `boundary` 抖动转移（0/1/6 天）；**保留人工触发记录**；抖动记录**归档不删除**（加 `archived: true`）；快照 100 条按新算法重算并叠放 `recomputed_from` 溯源 |
| L6 一致性 | `build_timeline` 以**运行时 `current_stage`/`current_stage_start` 为准**，静态史表只作补充；三者口径统一并加一致性自检 |
| L7 可运维 | 提供 `POST /api/market/merrill-clock/reevaluate`（已存在）的**幂等重算 + 归档**能力；加「人工锁定阶段」入口，避免算法再次抖动污染历史 |
| L8 测试 | 每指标一条「真实列名 fixture」用例；缺列/NaN/乱序/全缺 4 类确定性用例；防抖用例（连打同一象限不得重复写历史） |

## 5. 总体评估

### 5.1 架构评估（结论：基本健康，问题集中在「数据管道」与「连接生命周期」）

| 维度 | 评分 | 说明 |
|---|---|---|
| 架构分层 | **B+** | 后端 FastAPI + 领域 Mixin 拆分、前端零构建 SPA + 模块化（`__quantModules`）清晰；`merrill_clock/` 已按 `_core/_indicators/_history/_constants` 拆分，可维护性尚可 |
| 数据正确性 | **D** | **本次最大短板**。第三方数据适配靠「硬编码列名 + 缺省 0」，无契约测试；单位靠前端各自换算，无单一来源 |
| 稳定性/韧性 | **C+** | 数据源三源热备、降级占位做得不错；但**连接生命周期**（登录→WS）断裂，且降级文案会掩盖「未启动」 |
| 可观测性 | **C** | 有健康检查/自检/新鲜度，但**指标缺失不暴露**（把 0 当有效值上报「AKShare实时」），误导性比没有更糟 |
| 测试质量 | **B** | 3931 用例规模可观、门禁完善（覆盖率/令牌/对比度/版本纪律）；但**数据解析与单位口径**是盲区 |
| 用户体验 | **B-** | 视觉与信息架构成熟（原子层/令牌/动效治理到位）；本轮 5 项问题全在「用户每天盯着看」的核心页 |

### 5.2 根因归类（比逐个修更有价值）

1. **「取不到」被当成「等于 0 / 等于空」**（美林 4 指标、成交额除数、rise_speed）——这是本轮 3 个 P0 的**共同模式**：缺省值与真实值不可区分。
2. **生命周期只在「冷启动」接线一次**（WS 连接）——SPA 没有页面刷新，登录这类状态跃迁必须显式触发副作用。
3. **单位与口径散落前端**（千元/万元/亿元/手/股各算各的）——缺「数据契约 + 统一格式化」层。
4. **派生状态可以反向污染源数据**（零值覆盖好默认值、抖动写入历史）——缺「缺失即缺失」与「写入前守卫」。

> 结论：这 4 类模式**仍在其他模块潜伏**（行情聚合、资金流、龙虎榜、组合持仓都用类似 `get(..., 0)` 写法）。建议本迭代修 P0 的同时，落一个**「数据契约 + 缺失语义」小规范 + 1 个 lint/测试门禁**，把同类问题一次性按住，而不是逐个打补丁。

| 风险 | 等级 | 缓解 |
